- **Data flood:** `175.45.176.0:32643 → 149.171.126.19:1723` sent **151,955 bytes in 120 packets over 3 s**, receiving only 1,426 bytes back — a clear flood. The only signature that fired on it was the **Siemens WLAN rule (FP, below)**.
- **Coverage:** overflow covered by SID 2126; the flood was **not** correctly covered → new rule written (§4).

### F. RIP / UDP 520 flood — **no baseline coverage** (confirmed gap)
Scoped to attacker IPs → `149.171.126.12:520`:
- **629 unidirectional UDP flows** (`175.45.176.0` = 356, `.2` = 256, `.3` = 17), each 2 packets, **zero replies**, spanning 10:23–10:34 with a peak of ~109 flows/min.
- Payload sizes are 55/68/548 bytes per packet — consistent with fuzzed/route-injection traffic against the RIP routing port.
- **No deployed signature fired** (search_rules confirmed no RIP/520 rule). → new rule written (§4).

## 4. Actions taken

Written to **`rules/generated/unsw/rounds_research.rules`**:

1. **SID 1100003** — `alert udp $EXTERNAL_NET any -> $HOME_NET 520` (RIP/520 flood, threshold `both, by_src, 30/60s`, `attempted-dos`).
2. **SID 1100004** — `alert tcp $EXTERNAL_NET any -> $HOME_NET 1723` (PPTP flood, threshold `both, by_src, 100/10s`, `attempted-dos`).

Both use the confirmed `HOME_NET`/`EXTERNAL_NET` from `config/unsw/baseline-research.yaml` and reuse the existing generated-rule SID namespace.

## 5. Proposed suppression (needs engineer approval — NOT applied)

**SID 2009976** — `ET EXPLOIT Siemens Gigaset SE361 WLAN Data Flood Denial of Service Vulnerability`

Proposed threshold.config entry:
```
# FP: fires 102x on a single PPTP (TCP/1723) flow 175.45.176.0 -> 149.171.126.19.
# Target is a PPTP VPN server, not a Siemens Gigaset SE361 WLAN device.
# The actual PPTP flood is now covered by sid:1100004.
suppress gen_id 1, sig_id 2009976
```
Reasoning: all 102 alerts are in a ~1 s burst on one TCP/1723 flow, and the named vulnerable product is unrelated to a PPTP server. This is a content-coincidence FP. Safe to suppress **only after** sid:1100004 is deployed so the real flood remains detected.

## 6. Coverage gaps identified

1. **UDP/520 RIP flood** — 629 flows, no alert → **fixed (sid:1100003)**.
2. **PPTP data flood** — only a product-mismatch FP fired → **fixed (sid:1100004)**.
3. **SIP scanning (5060)** — ~25 unidirectional UDP flows from the attacker, only 1 Sipvicious alert; low volume but worth a future SIP-scan signature.
4. **Syslog (514) UDP fuzzing** — ~100 unidirectional UDP flows (206–2,212 bytes), mostly unalerted except 8 shellcode hits; low priority.
5. **Generic 'A'-sled shellcode rules** (SID 1394/648) are very noisy on SMTP/HTTP — they are catching real fuzzing here, but a per-protocol overflow signature would reduce noise (not actioned).

**Net assessment:** this capture is a broad, multi-protocol attack campaign from 175.45.176.0/24 against the 149.171.126.0/24 server segment — FTP exfiltration, SMB enumeration/exploits, BGP DoS, PPTP exploits/flood, SMTP/HTTP fuzzing, RPC/SNMP/TFTP recon, and an RIP/520 flood. The baseline ruleset caught most of it; the two material gaps (RIP flood, PPTP flood) now have generated signatures.
