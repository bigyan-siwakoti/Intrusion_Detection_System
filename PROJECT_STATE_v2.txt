1.1 SSH INVESTIGATION — CONCLUDED
----------------------------------

FINDING: SSH brute-force success is INVISIBLE to a network-based IDS.

What we checked:
  jq 'select(.event_type=="ssh" and .src_ip=="172.16.0.1")' \
    logs/tuesday-threshold-v2/eve.json

What Suricata logs for SSH:
  - ssh.client.software_version: "paramiko_2.0.0"
  - ssh.server.software_version: "OpenSSH_7.2p2 Ubuntu-4ubuntu2.2"
  - ssh.client.proto_version / ssh.server.proto_version: "2.0"

What Suricata CANNOT log for SSH:
  - Authentication result (success/failure) — encrypted inside the tunnel
  - Username attempted — encrypted
  - Number of auth attempts per connection — encrypted

Contrast with FTP:
  FTP sends completion codes in plaintext (530 = fail, 230 = success).
  Suricata captures these in .ftp.completion_code and .ftp.command fields.
  SSH auth is encrypted after key exchange — there is no equivalent field.

Conclusion: This is a STRUCTURAL limitation of network-based IDS for
encrypted protocols. It is not a Suricata bug or a rule gap. It means:
  - We can detect SSH brute-force ATTEMPTS (SYN packets, paramiko fingerprint)
  - We CANNOT determine if the brute-force SUCCEEDED
  - This is a real finding for the report — the boundary of what network IDS
    can see without TLS termination / host-based augmentation.


1.2 AI TRIAGE PIPELINE — FULLY BUILT
--------------------------------------

Architecture (changed from MCP to direct tool use):
  Suricata → eve.json → Python tools → Claude API (tool use) → Web UI (SSE)

Why not MCP: The MCP approach would have added a layer of indirection.
Direct tool use with Claude API is simpler and gives us fine-grained control
over streaming events for the web UI. Same capability, less plumbing.

FILES BUILT:

  src/__init__.py          — package init
  src/tools.py             — 7 tool functions with security controls
  src/prompts.py           — system prompt (~3,300 chars, 6-step triage)
  src/engine.py            — agentic loop with streaming, compaction, approval gate
  src/cli.py               — terminal runner with colored output
  src/server.py            — FastAPI SSE server
  src/static/index.html    — real-time dark-themed web UI with export
  requirements.txt         — anthropic, fastapi, uvicorn

TOOL INVENTORY (src/tools.py):

  Tool               Description                                 Security
  ─────────────────────────────────────────────────────────────────────────

  count_alerts        streaming signature aggregation             path-restricted

ENGINE DESIGN (src/engine.py):

  - Manual agentic loop (not tool runner) for fine-grained streaming control
  - MAX_TURNS = 30 per triage session
  - MAX_TOOL_RESULT_CHARS = 15,000 per tool result
  - Streaming: yields event dicts (thinking, text, tool_call, tool_result,
    suppress_proposal, usage, done, error) for UI consumption
  - Adaptive thinking: thinking={"type": "adaptive"}
  - Suppress approval gate: any write to threshold.config containing
    "suppress" is blocked → yields suppress_proposal event → requires
    approve_suppress callback to return True
  - Conversation compaction: on 413 BadRequestError, _compact_messages()
    trims tool results in older turns to 500 chars and drops thinking blocks
  - Handles pause_turn stop_reason for long-running turns

WEB UI (src/static/index.html):

  - Dark-themed, real-time streaming via Server-Sent Events
  - Controls: run selector (auto-populated from /api/runs), model selector
    (Sonnet 5, Opus 5, Opus 4.6, Haiku 4.5), start/stop buttons
  - Status bar: status, turn count, input/output token counters
  - Event rendering:
    - Thinking: dim, left-bordered, italic
    - Text: green, streaming
    - Tool calls: collapsible panels with input/output, auto-collapse >15 lines
    - Suppress proposals: yellow warning box
    - Done: green badge + rendered report (simple markdown→HTML)
    - Errors: red bordered box
  - Auto-scroll with scroll-position detection
  - Export Log button: downloads full timestamped .txt transcript of entire
    triage session (thinking, tool calls, results, report, token counts)

2.1 LLM NON-DETERMINISM / TOOL-RESULT SHAPING
-----------------------------------------------

PROBLEM: Same prompt + same data → materially different triage conclusions.

CLI run found FTP success via completion codes. Web run found "no evidence"
via byte-count inference. The user noticed and asked why.

DIAGNOSIS (from advisor review):

  1. The two runs did NOT see identical data. Between runs, tools.py and
     engine.py were patched (jq error capping, MAX_TOOL_RESULT_CHARS). The
     web run hit a jq error early, got the syntax hint, and was shaped by
     that interaction. Different tool surfaces → different reasoning paths.

  2. LLM temperature is a factor, but the mechanical cause is more
     interesting for the report: "identical prompt, identical model,
     different tool-result shaping → materially different conclusions."
     This is directly relevant to Experiment 1 (what context matters).

  3. The prompt's Step 3 says "Look at the protocol details (FTP completion
     codes, HTTP methods, SSH versions, etc.)" — this is a SUGGESTION,
     not a MANDATE. The model can choose to skip it.

2.3 PROMPT NEEDS ATTACK-AGNOSTIC IMPROVEMENT
----------------------------------------------

DO NOT add "always check FTP completion codes" — that hardcodes Tuesday's
answer. Wednesday is DoS (no FTP, no SSH). The fix must generalise.

Advisor-recommended prompt addition (attack-agnostic):

  "When determining whether an attack succeeded, prefer application-layer
   protocol events (event_type of ftp, ssh, http, dns, etc.) over flow-level
   byte counts. Before concluding a protocol's data is unavailable, list
   which event_type values are present in the log and confirm. Never claim
   a Suricata configuration setting is enabled or disabled without reading
   config/suricata.yaml."

This would have caught BOTH web-run errors:
  1. Using byte counts instead of FTP completion codes
  2. Claiming FTP app-layer logging was disabled


2.4 JQ ERROR HANDLING — FIXED BUT WORTH DOCUMENTING
-----------------------------------------------------

INCIDENT: Model wrote jq queries using unique/unique_by/group_by on
line-delimited JSON without slurping. This generates one error per line
in eve.json (millions of lines). First time: crashed the session (tool
result too large → 413 API error). Second time: error capping + hint
worked, model recovered.

FIXES APPLIED:
  - jq stderr capped at 10 lines + syntax hint about streaming (tools.py)
  - Tool results capped at 15,000 chars (engine.py)
  - Conversation compaction on 413 errors (engine.py)

POTENTIAL ADDITIONAL FIX (advisor suggestion):
  Add a count_event_types tool that returns distinct event_type values with
  counts. This is the orientation query both runs needed and neither could
  express cleanly. Same reasoning that made count_alerts worth having.


2.5 SUPPRESS APPROVAL GATE — UNTESTED EDGE CASE
-------------------------------------------------

The gate checks: "threshold.config" in file_path AND "suppress" in
content.lower(). A proposal phrased without the word "suppress" (e.g.
using "threshold" syntax instead) would bypass the gate. Not yet
triggered in practice, but Wednesday's DoS volume may produce suppress
proposals we haven't seen yet.

6. KEY LEARNINGS SINCE v1 (for the report)
================================================================================

- SSH auth results are encrypted. Network-based IDS can fingerprint the
  client (paramiko_2.0.0) and count connections, but cannot determine if
  a brute-force attack succeeded. This is a structural boundary of NIDS
  without TLS termination. FTP is the opposite — plaintext protocol means
  full visibility into auth outcomes.

- Same prompt, same model, same data → different triage conclusions. The
  mechanical cause is tool-result shaping: jq error recovery paths, output
  truncation, and hint text all influence the model's reasoning chain.
  This is a stronger and more defensible finding than "LLMs are
  non-deterministic" and is directly relevant to Experiment 1.

- jq queries on multi-GB eve.json files need streaming patterns. Using
  slurp operators (unique, group_by, [., inputs]) on 700MB+ files either
  times out or produces millions of error lines. Streaming (select + pipe
  to sort | uniq -c) handles any size.

- The suppress approval gate (human-in-the-loop for widening the profile)
  works as designed. The model proposed suppress rules during triage; the
  gate blocked the write and surfaced the proposal to the engineer.

- Conversation compaction (trimming old tool results on 413 errors) is
  essential for long triage sessions. Without it, a single bad jq query
  that produces large error output can permanently crash the session.

- A good tool surface matters more than a good prompt. The model's
  reasoning quality depends heavily on what tools are available and what
  their output looks like. count_alerts existing as a dedicated tool
  (instead of requiring the model to construct a complex jq pipeline)
  means the model reliably gets orientation data on turn 1.

- Export/logging is essential for reproducibility and the report. The web
  UI Export Log button captures the full transcript — every thinking block,
  tool call, tool result, and final report — as a timestamped .txt file.
  This is the evidence trail for the experiments.
