# Triage Report — logs/unsw-10-raw/eve.json

## 1. Big picture

- **799 alerts** total, across **163 unique signatures**.
- Attacker traffic overwhelmingly originates from the known attack range **175.45.176.0/24**:
  - `175.45.176.0` — 299 alert events
  - `175.45.176.2` — 113
  - `175.45.176.3` — 109
  - `175.45.176.1` — 91
- Top destinations are HOME_NET servers, most heavily `149.171.126.10` (182 alerts), then `.13/.19/.15/.16/.14/.17/.12/.11/.18`.
- Capture window is roughly **14:16–14:42 (2015-02-18 +09:30)**.

The alert mix is dominated by three categories:
- **Stream/parser noise** (SURICATA STREAM/HTTP/TLS/SMB/Frag decoder events) — e.g. SID 2210020 (80), 2210029/2210045, 2221029, 2260002. Informational; these are the result of the run not loading a threshold file (see §6).
- **RPC portmap recon** — 168 "Decode of an RPC Query" alerts (GPL portmap program probes).
- **Real exploit/recon campaigns** — detailed below.

## 2. Confirmed attacks

### A. Heartbleed exploitation — TRUE POSITIVE (confirmed data leak)
**Filter:** `event_type=="flow"` and `(src_port==7002 or dest_port==7002)`, attacker `175.45.176.0` → `149.171.126.10`.

Five TLS flows to `149.171.126.10:7002` (non-standard TLS port, test cert "vrt-bz") show the classic Heartbleed signature: tiny requests, huge responses:

| start | bytes to server | bytes to client |
|---|---|---|
| 14:19:38 | 5,768 | 504,298 |
| 14:18:58 | 5,060 | 504,080 |
| 14:19:16 | 5,414 | 503,962 |
| 14:19:09 | 3,408 | 233,374 |
| 14:19:27 | 5,060 | 504,074 |

- **~24 KB sent, ~2.25 MB returned** to the attacker across 5 sessions (each ~504 KB response = repeated ~64 KB heartbeat leaks).
- The custom recon rules **7600102 / 7600103** fired 79 + 66 times on this activity, but **no stock Suricata/ET heartbeat-leak rule fired**. The one custom parser rule (`7600101`, `tls.invalid_encrypted_heartbeat`) failed to load because Suricata 8.0.6 does not register that app-layer event (see suricata.log). So the actual leak was only visible via flow byte ratios + the custom recon-burst rules.

**Technique:** CVE-2014-0160 Heartbleed memory disclosure against a vulnerable TLS service on port 7002.

### B. FTP PASS format-string / overflow fuzz — TRUE POSITIVE (server accepted all logins)
**Filter:** `event_type=="ftp"` and `src_ip=="175.45.176.0"` and `dest_ip=="149.171.126.15"`.

- **59 `PASS` commands**, from **14:20:29 to 14:23:12** (~2m43s).
- **All 59 were answered `230 Login successful`** (filter: `select(.ftp.command=="PASS") | .ftp.completion_code[0]` → 59 × `230`).
- Payloads are a textbook wu-ftpd style fuzz set:
  - format strings: `%n%n…`, `%s%s…`, `%%n…`, `%%s…`, `%99999999s`, `%99999999d`, `%@%@…`
  - path/device fuzz: `../../…`, `aux`, `com1`, `con`, `\` runs
  - buffer fuzz: long `A` runs up to hundreds of bytes, `\xff` runs
- Stock **GPL 2101972** (PASS overflow) caught only **34 of 59** attempts; the success side was invisible to stock rules.

**Technique:** FTP format-string / buffer-overflow exploitation attempt against a permissive test FTP server.

### C. SSH connection burst — TRUE POSITIVE (recon/brute-force precursor)
**Filter:** `event_type=="flow"` and `src_ip=="175.45.176.0"` and `dest_ip=="149.171.126.13"` and `dest_port==22`.

- **10 distinct TCP connections** to `149.171.126.13:22` in **~1 second** (14:31:49.78–14:31:50.81).
- Each flow received only the server banner `SSH-2.0-OpenSSH_5.3p1`; no client auth completion was logged.
- Stock `ET SCAN Potential SSH Scan` (2001219) fired once; the custom `9500002` fired twice.

**Technique:** rapid SSH connection burst / scan (no evidence of successful authentication).

### D. SMB IPC$ enumeration and LSASS exploit attempt — TRUE POSITIVE
- Stock SMB rules `2102466` (18) and `2100538` (16) fired across many attacker→server pairs.
- SMB app-layer events show:
  - `SMB1_COMMAND_SESSION_SETUP_ANDX` with **anonymous** user and `TREE_CONNECT_ANDX` to **IPC$** (e.g. `175.45.176.3 → 149.171.126.19`).
  - `SMB1_COMMAND_NT_CREATE_ANDX` filename overflow fuzz (`((((((…`, `}}}}…`, `{{{{…`, `>>>>…`, `<<<<…`) from `175.45.176.0 → 149.171.126.18`.
- **LSASS exploit attempt** `2102511` (CVE-2003-0533, `DsRolerUpgradeDownlevelServer`) fired 4 times in one flow: `175.45.176.2:30736 → 149.171.126.19:139`, 14:42:08–14:42:09. Flowbits confirmed `smb.tree.connect.ipc` + `netbios.lsass.bind.attempt`.

**Technique:** SMB share enumeration + a targeted LSASS DCE/RPC exploit attempt over NetBIOS.

### E. TFTP overflow and directory traversal — TRUE POSITIVE (attempts, no data returned)
- `GPL TFTP Put` (2100518) fired **24 times** on TFTP WRQ requests with oversized random filenames (e.g. `175.45.176.1 → 149.171.126.19:69`, `175.45.176.0 → 149.171.126.14:69`).
- `GPL TFTP GET passwd` (2101443) fired twice on `175.45.176.0 → 149.171.126.17:69` for `../../../../../../../../../../../passwd`. The flow shows **2 packets to server, 0 returned** — the read did **not** succeed.
- Additional traversal read: `175.45.176.1 → 149.171.126.19:69` for `/O5sLsl/../../../../../boot.ini`.

**Technique:** TFTP buffer-overflow (oversized filenames) and directory-traversal read attempts.

### F. RPC portmap sweep — TRUE POSITIVE (recon)
- 168 RPC query alerts (GPL portmap program probes: `rstatd`, `amountd`, `ypserv`, `sadmind`, `mountd`, `rexd`, etc.) from the attacker range sweeping TCP/UDP **111** across HOME_NET servers.
- The existing generated rule family for RPC sweep consolidation is already in `unsw_triage.rules`.

### G. Broad web exploit scanning — TRUE POSITIVE attempts, no confirmed compromise
Many one-off ET WEB_SERVER / EXPLOIT alerts from the attacker range, including:
- PHP code injection: `2019182` (eval base64_decode), `2019804` (php://input) — `175.45.176.3 → 149.171.126.12:80` at 14:18:30.
- Cisco IOS exec probe `/level/52/exec//show` and `/level/96/exec//show` (matching existing generated rule `7600401`).
- SQLi, cmd.exe, Struts OGNL, Sophos/SiteScope/Zavio/Sinapsi/Cisco HyperFlex RCE probes, ISAPI `.ida/.idq`, ColdFusion admin, etc.
- HTTP events show many requests receiving `200`, but the specific exploit POSTs/URIs typically had `status:null` (no captured response) — I found **no evidence of successful compromise**.

### H. SMTP malicious attachment delivery — TRUE POSITIVE attempt, delivery unconfirmed
`ET HUNTING SUSPICIOUS SMTP EXE` (2017886 ×2, 2017887 ×1, 2017890 ×1) fired on SMTP traffic from the attacker range to HOME_NET port 25. SMTP app-layer events show HELO/MAIL FROM/RCPT TO only; no SMTP reply codes were logged, so I cannot confirm the messages were accepted.

## 3. Likely false positive

### ET SHELLCODE Rothenburg Shellcode — SID 2009247 (5 alerts)
All 5 alerts are in the **to_client** direction (HOME_NET server → attacker):
- 4 × HTTP response bodies (`.wmf`, `.asmx`, `.html` content) and 1 × VNC/RFB server data (`149.171.126.11:5900 → 175.45.176.0`).

The attacker was the **client**; the signature is matching byte patterns inside benign/generated server response content, not an exploit payload sent by the attacker. This is characteristic of the Rothenburg signature false-positiving on binary/text response bodies.

# server response bytes. False positive for this dataset.
suppress gen_id 1, sig_id 2009247
```

|---|---|---|

| 7601002 | TFTP directory traversal read | `../passwd` and `/…/../../boot.ini` reads in §E (stock 2101443 only catches literal `passwd`) |
| 7601003 | FTP PASS format-string fuzz campaign | the `%n/%s/%99999999s/%@` family in §B that stock 2101972 partially misses |

## 5. Coverage gaps identified

1. **Heartbleed leak volume itself is not directly alertable.** Suricata's `tls.invalid_encrypted_heartbeat` app-layer event is unavailable in this build (rule `7600101` failed to load), and a single-packet rule cannot sum `bytes_toclient`. The leak is only inferred from recon-burst rules + flow byte ratios. A flow/streaming metric (e.g. post-detection flow byte analysis) is the realistic fix.
2. **SMB filename overflow fuzz** (`NT_CREATE_ANDX` with repeated `(`, `}`, `{`, `>`, `<` filenames) was not alerted — only the parser event `2225006` fired. Suricata 8.0.6 lacks `smb.command` keyword support (see load errors), so an app-layer SMB rule could not be written.
3. **Stock web rules are one-shot per payload**; there is no consolidation rule for the broad web exploit sweep. Acceptable given the volume, but a campaign-level web scanner rule could help future triage.
4. **The run did not load a threshold file** (`threshold-config: Error opening file ""` in suricata.log), which is why 80×`2210020` and other stream/parser noise dominates the alert count. Many of those SIDs already have suppress lines in `config/threshold.config`; they simply were not applied.

## 6. Notes on the run configuration

- suricata.log shows **10 rule files processed, 52,670 rules loaded, 3 rules failed** (the failed rules were `smb.command` / `dcerpc.iface` rules from `thursday_webattacks_infiltration.rules`, plus the TLS heartbeat parser-event rule).
- The custom Heartbleed recon rules that fired (`7600102/7600103`) and the SSH campaign rule (`9500002`) come from `wednesday_heartbleed.rules` and `bruteforce_campaigns.rules`, not from the UNSW-validation file `unsw_triage.rules`. My additions re-anchor the two missing patterns into `unsw_triage.rules` so future UNSW validation runs carry them.
