1.1 AI TRIAGE ENGINE (COMPLETE)
-------------------------------

Architecture:
  Suricata (pcap) --> eve.json --> AI Triage Engine --> Rules + Suppress Proposals
                                       |
                                   Web UI (live stream)

The engine is ~1,075 lines of Python across 6 files in src/:

  src/engine.py      (133 lines)  Agentic triage loop. Provider-agnostic.
                                  Sends messages, executes tool calls, handles
                                  streaming, enforces safety gate (suppress
                                  proposals need human approval). MAX_TURNS=100.

  src/tools.py       (380 lines)  8 tools the AI can use:
                                    - query_eve_json: run jq on eve.json
                                    - count_alerts: group alerts by signature
                                    - count_by: generic NDJSON aggregation
                                    - read_file: read any project file
                                    - write_file: write to threshold.config
                                                  or rules/generated/
                                    - append_to_file: append to writable files
                                    - run_suricata: run Suricata on a pcap
                                    - list_directory: list files with sizes

  src/providers.py   (319 lines)  Provider adapters for Claude (Anthropic API)
                                  and DeepSeek (OpenAI-compatible API). Same
                                  triage loop, swappable model backend. Handles
                                  streaming, tool call format conversion,
                                  context compaction.

  src/prompts.py     (79 lines)   System prompt with 6-step triage procedure:
                                  1. Big picture (count_alerts)
                                  2. Categorise signatures
                                  3. Investigate potential attacks
                                  4. Deep-dive on confirmed attacks
                                  5. Take action (rules or suppress proposals)
                                  6. Write report

  src/server.py      (72 lines)   FastAPI web server. SSE streaming to browser.
                                  Serves the web UI and handles triage requests.

  src/cli.py         (92 lines)   CLI runner. Alternative to web UI.
                                  Outputs triage to terminal with timestamps.

  src/static/index.html           Web UI. Model dropdown (Claude Opus 5,
                                  DeepSeek V3), run selector, real-time triage
                                  streaming, export to text file.

KEY DESIGN DECISIONS IN THE ENGINE:
  - Provider adapter pattern: same loop for all models = fair comparison
  - count_by tool: solves NDJSON aggregation problem that caused DeepSeek to
    fail (group_by/min_by/max_by don't work on streaming JSON). Uses Python
    collections.Counter, no shell injection risk.
  - Safety asymmetry: detection rules auto-deploy to rules/generated/,
    suppress proposals are shown to engineer and blocked until approved.
  - Tool results capped: 15K chars for Claude, 8K for DeepSeek (smaller
    context window). Truncation hints point to count_by.

6. KEY FINDINGS SO FAR (for the report)
================================================================================

  1. BOTH MODELS FOUND THE SAME ATTACKS. Claude and DeepSeek V3 reached
     identical substantive conclusions on every attack day tested. The
     findings are model-independent.

  2. TOOL DESIGN MATTERS AS MUCH AS MODEL CHOICE. DeepSeek failed completely
     until we added count_by (NDJSON aggregation tool). "Cheaper model needs
     better-shaped tools" is a real finding.

  3. AI-AUTHORED RULES OUTPERFORMED STOCK RULES FOR SPECIFIC ATTACKS. The
     Slowloris toolkit fingerprint rule caught 187 attack requests vs stock
     ET's 2-4. The Hulk flood rule caught 95 attacks the stock ruleset
     missed entirely.

  4. THE AI ITERATIVELY IMPROVES THE SENSOR. Across multiple passes:
     - It writes detection rules (more signal)
     - It proposes suppressions (less noise)
     - It validates its own rules and finds bugs
     - It refines suppress proposals based on what it learns
     This is convergence without ML.

  5. RAW VS TUNED: the raw (no-suppression) run found a detection gap the
     tuned run couldn't see, because the tuned version suppressed the only
     signal that hinted at the Hulk flood. Pre-tuning helps efficiency
     (381 vs 2.3M alerts) but can hide gaps.

  6. COVERAGE GAPS IN STOCK ET RULESET:
     - SSH brute force: 31 alerts for ~2,980 attack flows (SYN-only rule)
     - Slowloris: 2-4 alerts for 167K+ attack requests (rate-based rule)
     - Hulk GET flood: no dedicated signature at all
     - FTP default credential login: no stock rule for bare 230 from external

  7. AI RULES ARE INSPECTABLE. Every rule is a standard Suricata rule that
     a human can read, validate, and modify. Detection stays rule-based.
     The AI does the analyst's work, not the engine's work.

  8. SAFETY ASYMMETRY WORKS. Detection rules deploy freely (worst case:
     extra alerts). Suppress rules need human approval (worst case: blind
     IDS). This prevents the AI from silently degrading the sensor.
